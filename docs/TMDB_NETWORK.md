# TMDB: DNS и маршрут до изображений

## Что подтверждено диагностикой 21 октября 2026

- Пользователь сообщил, что изображения работали напрямую и пропали примерно за неделю до диагностики. Правило Podkop добавлялось только в день проверки; нельзя считать его причиной первоначального сбоя.
- Системное разрешение имён TMDB возвращало loopback. Google DoH также возвращал loopback для CDN-алиаса; Cloudflare DoH возвращал публичные адреса.
- API по публичному адресу с правильным TLS-именем отвечал 401 без ключа — соединение работало.
- Один и тот же публичный адрес картинки не отвечал напрямую с Windows и CachyOS, но через уже настроенный интерфейс awg0 на OpenWrt возвращал 200 image/jpeg.
- Пользователь подтвердил открытие исходного URL постера в браузере после добавления правила. Изменённый URL давал 404; это не доказывает недоступность исходного URL или источник ответа.
- В текущем текстовом списке обнаружен tmdb.com. Он не охватывает image.tmdb.org и api.themoviedb.org. Domain Resolver выбранной VPN-секции был выключен.

Точная причина изменения прямой доступности неделю назад не установлена. Открытие локальной панели при домене TMDB согласуется с неверным разрешением имени, но точный путь до панели отдельно не подтверждён. Ответ браузера 499 antivirus относится к конкретному запросу Windows и не объясняет всю домашнюю сеть.

## Исправление существующей VPN-секции OpenWrt

Запускать **в SSH OpenWrt, в ash**, не на CachyOS:

```sh
sh /root/fix-podkop-tmdb.sh main
```

Скрипт `scripts/fix-podkop-tmdb.sh`:

1. Требует существующую VPN-секцию с заданным интерфейсом и отсутствие неприменённых UCI-изменений.
2. Сохраняет `/etc/config/podkop` в локальную закрытую резервную копию и печатает команду отката.
3. Добавляет `tmdb.org`, `themoviedb.org`, `tmdb-image-prod.b-cdn.net`, сохраняя существующий текстовый/динамический список и комментарии.
4. Включает Domain Resolver **выбранной VPN-секции**: Cloudflare DoH, адрес `1.1.1.1`. Это меняет разрешение реальных имён всех доменов этой VPN-секции, не только TMDB. Глобальный и bootstrap DNS не меняются.
5. Перезапускает Podkop и проверяет синтаксис конфигурации sing-box. При ошибке восстанавливает конфиг. Перезапуск кратковременно затрагивает соединения через Podkop.

Параметры Domain Resolver и отправка его DNS через VPN-outbound сверены с [исходниками Podkop 0.7.22](https://github.com/itdoginfo/podkop/blob/0.7.22/podkop/files/usr/bin/podkop). Сам VPN-интерфейс, ключи и mixed proxy скрипт не меняет. Конкретные IP CDN не сохраняются.

Проверки UCI сохранения/отката выполняются локально с подставными командами, без изменения сети машины разработки. Конфигурация на реальном OpenWrt и итоговая загрузка требуют проверки пользователя.

## Проверка после установки

Полностью перезапустить браузер/Lampa, чтобы старое разрешение имён не осталось в соединениях приложения. Проверять исходный URL и фактические изображения карточки/серий. Возврат FakeIP при использовании Podkop сам по себе не является ошибкой: это штатное доменное перенаправление. Синтаксическая проверка sing-box не заменяет проверку доступности картинки.

Правила OpenWrt действуют для проходящих через него клиентов. Сервер выше OpenWrt за MikroTik не начинает использовать его VPN автоматически. Для централизованной загрузки потребуются отдельный проверенный прокси или другая согласованная схема; этот скрипт не открывает порты и не меняет маршруты сервера.

Для отката использовать напечатанную команду `sh /root/fix-podkop-tmdb.sh --rollback BACKUP_PATH`. Резервная копия может содержать VPN-секреты: она остаётся только на роутере, её нельзя добавлять в Git.
